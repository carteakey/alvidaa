## 1. Host-side trap: a managed Mac cannot serve the TV (workaround found)

The TV was reachable (`36669` open at the DHCP lease), but the launcher could
not be served from the Mac:

- macOS Application Firewall: *"blocking all non-essential incoming
  connections"*, stealth mode on, and Python listed as
  **Block incoming** — two launcher URLs produced Chrome `ERR_EMPTY_RESPONSE`
  (`-324`) on the TV.
- `socketfilterfw --unblockapp` → **"Firewall settings cannot be modified from
  command line on managed Mac computers."** The Mac is MDM-managed
  (Microsoft Defender network + endpoint security extensions active).
- Symptom shape: TCP connects, then the accepted socket dies
  (`getpeername: EINVAL`, `readline: ENOTCONN`). Even a self-connection to the
  Mac's own LAN address fails, while `127.0.0.1` is fine. This is not the TV
  and not the server.
- `/usr/bin/ruby` (Apple-signed) was auto-allowed when it listened, so the
  block is policy-shaped, not per-binary — but Python, and every other app,
  stayed blocked.

**Workaround that unblocked the session:** a plain-TCP tunnel on the *outbound*
side — `bore local 8765 --to bore.pub` → `bore.pub:<port>` → the TV loaded
`http://bore.pub:<port>/…`. Plain TCP (not HTTPS) matters: the page hardcodes
`ws://`, so an https tunnel would hit mixed-content blocking.

The load-bearing insight for root work: **a page served from anywhere still
runs on the TV and still reaches `http://localhost:9009` / `localhost:9888` /
the superwatch socket.** The tunnel does not weaken the chain at all — the
browser context is what matters, not the origin.

Caveat to keep in mind: the tunnel is a public URL while it runs. Tear it
down when done; the page content is not secret but the tunnel is third-party.

### 6a. SOLVED the same session — the IPK, not the command, was wrong

`82` is the correct install command. The proof is the vendor's own wrapper:
superwatch runs `/usr/local/scripts/ipk_install.sh` (readable, mode 555) with

```
session_id="$1"; ipk_path="$2"; pkg_name="$3"; options_string="$4"
```

and that script runs `opkg --force-reinstall install "${ipk_path}"` as root,
then writes the outcome to `/tmp/ipk_install_result` (chmod 640, **chown
314:314**, so it is readable as uid 314 — the direct readback lane) and
`/tmp/ipk_install_status`.

Our failed attempt left:

```json
{"code": 3, "sessionId": 713, "msg": "opkg install /APPS/re-proof-tar.ipk failed:
  error: install_app_configs: Invalid input parameters.
  error: opkg_install_pkg: Failed to extract data files for re.prooft."}
```

So two independent faults in the minimal IPK:

1. **`data.tar.gz` was empty** → "Failed to extract data files".
2. **`install_app_configs` rejected the control file.** The vendor `opkg`
   (181 KB, patched) carries the strings `AppId`, `AppName`,
   `Invalid appId: %s`, `Failed to convert appId '%s' to a valid uid` and
   `install_app_configs`. It reads `/APPS/pkgs/pkgAppInfo.json` and requires
   those fields.

With `Package: tv.vidaa.app.reproof`, `AppId: 900`, `AppName: …` and a
one-file `data.tar.gz`, the same frame `802:82:802;/APPS/re-proof3.ipk;…`
returned **rc 0**, `opkg_install_status` reached `step:finish`, and the
postinst ran as root:

```
POSTINST_RAN
Uid:	0	0	0	0
Gid:	0	0	0	0
CapEff:	000001ffffffffff
```

`/APPS/.re_root/PROOF` is `mode 644 uid 0`, so uid 314 reads the proof.

As root, `/config` remounts rw and back cleanly (`mount -o remount,rw /config`
→ OK, then `remount,ro` → OK), and both INIs are `-r--r--r-- root root` with
identical build mtimes and atimes — the atime does not reveal which one the
middleware read. `/var/log/messages` is root-only (`EACCES` to uid 314) and
was copied out to `/APPS/.re_root/messages.txt` by a postinst for reading.

**Root is achieved as one-shot uid 0.** Persistence (a boot hook, or a shell)
is the next step and has not been done.

The natural next step for any further work (including EDID) is to make the
postinst do the task directly and write its result into `/APPS/.re_root/`
(mode 644), rather than chasing a persistent shell: the round trip is one IPK
build plus one install, and each run is reversible by installing the next.
A boot hook (`serviceList.json` append, or the `re_sshd` service) is what a
persistent shell would need; that is deliberately out of scope while the goal
is EDID.
